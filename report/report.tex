% ---------------- Abstract ----------------
\begin{center}{\large\bfseries ABSTRACT}\end{center}
Manual testing is the foundation of software quality assurance: a tester studies the requirements, designs test cases, executes them by hand in the real application and records what actually happens. In this project the complete manual testing process is applied to Swag Labs (\url{https://www.saucedemo.com}), a publicly available demo e-commerce website that offers login, a product catalogue, a shopping cart and a checkout flow. The site provides six test user accounts, several of which deliberately expose functional, visual and performance defects, which makes it an ideal subject for learning defect detection and reporting.

The work followed the standard test life cycle. A test plan defined the scope, strategy, environment and entry/exit criteria. Twenty test scenarios were derived from the features of the application and expanded into thirty-nine test cases written in an Excel sheet with pre-conditions, steps, test data, expected result, actual result, status and priority. Black-box techniques such as equivalence partitioning, boundary value analysis and error guessing were used to design positive and negative cases, especially for the login and checkout forms. Every test case was executed manually in Microsoft Edge on Windows 11 with the appropriate test user and evidence screenshots were captured.

Twenty-eight test cases passed and eleven failed. The failures were analysed and consolidated into nine defect reports, each with severity, priority, steps to reproduce, expected versus actual behaviour and a screenshot. The defects range from a critical checkout blocker to wrong product images, broken sorting, wrong prices, missing input validation and a cart that survives logout. A requirement traceability matrix links every requirement to its test cases. The outcome is a complete and reproducible manual testing package that demonstrates test planning, test design, execution, defect reporting and traceability.

\section{Problem Statement Definition}\label{sec:ps}
Perform manual testing of an e-commerce website (Swag Labs, \url{https://www.saucedemo.com}) by preparing a test plan and test scenarios, designing positive and negative test cases in an Excel sheet, executing them by hand with the available test users, recording actual results, and documenting all defects found in structured bug reports with severity, priority, steps to reproduce and evidence. Regular-expression style validation rules (e-mail, numeric postal code, name formats) are used to design the test cases for the input forms.

% ---------------- 2 ----------------
\section{Software Requirements Specification}\label{sec:srs}
\subsection{Introduction}\label{sec:srs1}
Swag Labs is a web-based demo online store. A customer logs in with a username and password, sees a list of six products with name, image, description and price, sorts them by name or price, adds products to a shopping cart, reviews the cart, enters first name, last name and postal code at checkout, reviews the order summary with item total, tax and total, and finishes the order. A side menu offers All Items, About, Logout and Reset App State. The site provides six test users with the same password \texttt{secret\_sauce}: \texttt{standard\_user} (normal behaviour), \texttt{locked\_out\_user} (login refused), \texttt{problem\_user} (functional bugs), \texttt{performance\_glitch\_user} (slow), \texttt{error\_user} (errors) and \texttt{visual\_user} (layout bugs).

\subsection{Scope}\label{sec:srs2}
\textbf{In scope:} functional, negative and UI testing of the login module, products page (listing, sorting, images, prices), cart (add, remove, badge count, persistence), checkout (form validation, totals, order completion), side menu and logout, and protected page access.

\textbf{Out of scope:} the payment gateway (the demo uses a fixed dummy card), load and security testing, mobile devices, and browsers other than Microsoft Edge.

\subsection{Requirements}\label{sec:srs3}
Functional requirements of the application under test:
\begin{itemize}[nosep]
  \item REQ-01: User can log in with valid credentials and is blocked otherwise.
  \item REQ-02: Products are listed with correct details and can be sorted.
  \item REQ-03: User can add and remove products in the cart.
  \item REQ-04: Checkout validates customer information.
  \item REQ-05: Order overview shows correct totals and the order can be completed.
  \item REQ-06: Navigation menu and logout work; protected pages need login.
\end{itemize}
Software requirements for testing:
\begin{itemize}[nosep]
  \item Windows 11 (any OS with a modern browser is sufficient)
  \item Microsoft Edge 142 (or Google Chrome)
  \item Microsoft Excel / LibreOffice Calc for the test case sheet
  \item Python 3 with openpyxl and selenium (only for generating the workbook and re-capturing evidence screenshots)
  \item Internet connection to \url{https://www.saucedemo.com}
\end{itemize}

% ---------------- 3 ----------------
\section{System Implementation}\label{sec:impl}
\subsection{Technologies and Tools}\label{sec:impl1}
\textbf{Microsoft Edge} is the browser in which all test cases were executed. Its developer tools were used to inspect error messages and element states.

\textbf{Microsoft Excel} holds the test artifacts in one workbook, \texttt{SwagLabs\_Test\_Cases.xlsx}, with four sheets: Test Cases, Defect Reports, RTM (requirement traceability matrix) and Summary. Each test case row has ID, module, title, pre-condition, test steps, test data, expected result, actual result, status, priority, defect ID and evidence file.

\textbf{Python with openpyxl} generates the Excel workbook and the Markdown documents from a single data file, so that the sheet, the documents and this report always agree. \textbf{Selenium} was used only to re-create the evidence screenshots in a repeatable way.

\textbf{Git and GitHub} store all artifacts: \url{https://github.com/VishwajeetTulse/ecommerce-manual-testing}.

\subsection{Test Design Approach}\label{sec:impl2}
Black-box techniques were applied to design the test cases:
\begin{itemize}[nosep]
  \item \textbf{Equivalence partitioning:} username $\in$ \{valid, empty, unknown, locked\}; password $\in$ \{correct, wrong, empty\}; first/last name $\in$ \{letters, digits, symbols, empty\}; postal code $\in$ \{digits, letters, empty\}. One test case per class.
  \item \textbf{Boundary value analysis:} empty fields and single-character inputs on the forms.
  \item \textbf{Error guessing:} the special test users (\texttt{problem\_user}, \texttt{error\_user}, \texttt{visual\_user}, \texttt{performance\_glitch\_user}) were used to provoke failures.
  \item \textbf{Regular-expression rules} for the checkout form: name must match \texttt{\^{}[A-Za-z ]+\$} and postal code must match \texttt{\^{}[0-9]\{5,6\}\$}; test data was chosen on both sides of each rule.
\end{itemize}
Severity scale: Critical (blocks a main flow), High (major feature wrong), Medium (works partly or with a workaround), Low (cosmetic). Priority (High/Medium/Low) states how soon the defect should be fixed.

\section{Working}\label{sec:work}
\subsection{Test Scenarios and Test Cases}\label{sec:work1}
Twenty test scenarios were written, for example: verify login with valid, empty, wrong and locked-out credentials; verify sorting by name and price; verify adding products updates the cart badge; verify mandatory field validation on the checkout form; verify overview totals and tax; verify logout and protected page access. Each scenario was expanded into one or more of the 39 test cases. The distribution is: Login 8, Products 8, Cart 6, Checkout 11, Menu 3, UI 3.

\section{Advantages and Limitations}\label{sec:adv}
\textbf{Advantages}
\begin{itemize}[nosep]
  \item Finds real functional, visual and performance defects that an automated script would not look for.
  \item Needs no programming; the Excel template can be reused for any web application.
  \item Every failure is reproducible because steps, data and evidence are recorded.
  \item Requirement traceability shows exactly which features have been tested.
  \item Using the special test users demonstrates error guessing effectively.
\end{itemize}
\textbf{Limitations}
\begin{itemize}[nosep]
  \item Manual execution is slow (about two hours for 39 cases) and must be repeated after every change.
  \item Results depend on the tester's attention; human error is possible.
  \item Only Microsoft Edge on desktop was covered; no mobile or cross-browser testing.
  \item The application is a public demo that cannot be fixed, so the defects remain open.
\end{itemize}

% ---------------- 6 ----------------
\section{Conclusion}\label{sec:concl}
This project carried out the complete manual testing process on a real e-commerce website. Starting from a test plan and twenty scenarios, thirty-nine test cases were designed with black-box techniques and executed by hand with six test users. Eleven failures were traced to nine defects, documented with severity, priority, reproduction steps and screenshots, and a traceability matrix links every requirement to its tests. The work shows that systematic manual testing with well-chosen negative cases and special test users finds a wide range of functional, visual and performance defects. The stable passing test cases were later converted into automated Selenium scripts in the companion automation project, and the defect reports can be tracked in a tool such as Jira in future.
